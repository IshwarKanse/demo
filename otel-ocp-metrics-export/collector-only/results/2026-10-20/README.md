# Collector-only sizing run, 2026-10-20, OpenShift 5.0 on AWS, product collector 0.158.0

Cluster: OpenShift 5.0.0-0.nightly-2026-10-19-060022 on AWS, 3 control plane nodes (m6i.xlarge, 3.5 CPU
and 14.2 GiB allocatable, 250 pods each) and 4 workers (m5.4xlarge, 15.5 CPU and 58 GiB allocatable,
250 pods each), 271 pods running before the idle pods. The same cluster carries the option 1 setup
(the platform and user workload Prometheus remote-write about 30,000 to 53,000 samples/s to the option 1
collector; the rate grows with the idle pods because Prometheus scrapes them too, recorded per run).
Operator: Red Hat build of OpenTelemetry 0.158.0-202610151241 from OperatorHub with its default collector
image `registry.redhat.io/rhosdt/opentelemetry-collector-rhel9@sha256:af76e9b5...` (no `spec.image`).

Configuration under test: the PoC manifests of this directory's parent in the sizing shape
(`scripts/run-matrix.sh`): platform metrics to the nop sink collector, the collectors' own telemetry to
the vendor stand-in Prometheus (for `collect.sh`) and to the user workload monitoring PodMonitor
(`07-uwm-podmonitor.yaml`, the measurement instrument read by `../../scripts/export-series.sh` through
the Thanos Querier). Documented resources: node collector requests 50m/192Mi and limits 500m/512Mi,
cluster collector requests 500m/1Gi and limits 2 CPU/4Gi; `memory_limiter` 80/20; item-sized
`sending_queue` of 200,000 (cluster) and 50,000 (node) items with `block_on_overflow`; exporter-side
batching; `retry_on_failure.max_elapsed_time: 0`. The cluster collector runs the full PoC catalog: 45
platform endpoint jobs plus the 4 optional kubelet jobs through the API server node proxy (`/metrics`,
`/metrics/cadvisor`, `/metrics/resource`, `/metrics/probes`), 49 jobs in total; the "documented shape"
runs leave the 4 kubelet jobs out, which is what the documentation module shows.

Matrix, 20 minute windows after 5 minutes of settling (the long window: 150 minutes at a 60 s step),
every run exported to `raw/<run>/<metric>.csv` with its metadata in `runs.json` (cluster shape, pods per
node, variant, configuration, outage markers); `summary.md` is generated by `render-charts.py`,
`table.md` holds the `collect.sh` rows read from the vendor Prometheus as a cross-check:

- idle-pod tiers 0, 300, 600, 850 and 1,200 (271, 571, 871, 1,121 and 1,471 pods running; the 4 workers
  hold about 890 extra pods at 250 pods per node, the 1,200 tier puts the rest on the control plane
  nodes through a toleration; 1,500 would need a KubeletConfig and node reboots, not done on a shared
  cluster);
- the scale-out variant at the top tier: StatefulSet with 2 replicas, target allocator
  (`prometheusCR.enabled: false`) and `k8s_leader_elector` (the operator webhook refuses a mode change on
  an existing CR, the script deletes and recreates it);
- the documented shape (45 jobs, no kubelet proxy jobs) at the top tier and at 0 idle pods;
- interval tiers at the top tier: 60 s and 15 s instead of 30 s (same series, different sample rate);
- a 150 minute window at the top tier;
- a 5 minute backend outage at the top tier (sink scaled to 0 through its CR) without and with the
  `file_storage` extension on the cluster collector queue.

## Findings

Cluster collector, one Deployment replica, 49 jobs (kubelet proxy jobs included), 30 s interval:

| pods running | data points/s | CPU avg / p95 | working set MiB avg / max | RSS MiB max |
|---|---|---|---|---|
| 271 | 6,346 | 0.10 / 0.10 | 948 / 981 | 1,052 |
| 571 | 9,601 | 0.14 / 0.15 | 1,246 / 1,302 | 1,325 |
| 871 | 12,838 | 0.18 / 0.19 | 1,717 / 1,804 | 1,755 |
| 1,121 | 15,538 | 0.21 / 0.22 | 2,082 / 2,226 | 2,086 |
| 1,471 | 19,428 | 0.24 / 0.28 | 2,510 / 2,628 | 2,458 |

- Both CPU and memory are linear in the pod count: working set 550 MiB + 1.34 GiB per 1,000 pods, CPU
  0.07 + 0.12 cores per 1,000 pods, 3,400 + 10,900 data points/s per 1,000 pods (least-squares fit over
  the five tiers). No refused point, no restart, no exporter failure in any tier. The `queue max`
  column of `summary.md` is a sampling artifact: the 30 s monitoring scrape repeatedly catches the moment
  a large cAdvisor scrape (55,000 to 79,000 points for a node with 250 pods) is enqueued; read directly on
  the collector the queue is a few hundred items with no in-flight request.
- The per-pod cost is the kubelet proxy jobs, above all `/metrics/cadvisor`: the documented shape
  without them costs 0.05 cores and 629 MiB working set (2,437 points/s) at 1,461 pods against 0.24
  cores and 2,510 MiB with them, and the API server node proxy requests drop from 1.2/s to 0.2/s.
  With the `kubelet_stats` receiver of the node collector already covering pods and containers, the
  cAdvisor job is only needed when the `container_*` Prometheus names must be kept.
- Interval tiers at 1,461 pods: 60 s gives 9,673 points/s at 0.12 cores and 2,157 MiB, 30 s 19,428 at
  0.24 cores and 2,510 MiB, 15 s 38,668 at 0.49 cores and 2,273 MiB: CPU follows the sample rate
  (about 1.25 cores per 100,000 data points/s; a histogram or summary counts as one point, so the
  number is not comparable one to one with option 1's samples/s), memory follows the series count.
- Scale-out at 1,463 pods: two StatefulSet replicas with the target allocator use 0.25 cores and
  2,790 MiB together (1,682 MiB on the busiest replica against 2,510 MiB for the single Deployment
  replica); the target allocator shards targets, not series, so the kube-apiserver target (about
  228,000 series) stays on one replica and the split is uneven. The target allocator itself costs
  3 millicores and 100 MiB.
- Node collector (one pod per node, `host_metrics` and `kubelet_stats`): the busiest node (250 pods)
  uses 0.005 cores, 72 MiB working set (76 max) and 153 MiB RSS; at 15 s interval 0.011 cores. All 7
  nodes together produce 480 points/s at 271 pods and 1,720 at 1,471. The documented limits
  500m/512Mi are an order of magnitude above the need.
- Control plane cost: the node proxy requests are 1.2/s for 7 nodes at 30 s (one `kubelet_stats`
  and four prometheus receiver scrapes per node per interval), 0.6/s at 60 s, 2.3/s at 15 s, 0.2/s
  without the kubelet proxy jobs. kube-apiserver CPU stays at 0.33 to 0.40 cores for the three
  instances in every tier and its working set grows from 8.1 to 9.5 GiB with the pods, not with the
  collectors (9,409 MiB without and 9,474 MiB with the kubelet proxy jobs at the same pod count).
- 5 minute backend outage at 1,461 pods, in-memory queue: the cluster collector filled its 200,000-item
  queue after 49 s and then blocked its scrapes for the rest of the outage (about 2 million points,
  3 minutes of control plane data, were never scraped: pull receivers have no upstream buffer), no
  refused point, no restart; after the sink came back it drained in about 75 s at up to 32,000
  points/s with the working set peaking at 3,183 MiB, just under the memory_limiter soft limit of the
  4Gi limit (3,277 MiB). The node collectors reached 46,000 of their 50,000 items per node at the end
  of the five minutes, lost about 40 s of data and drained in the same 75 s (RSS peak 177 MiB).
- The same outage with the `file_storage` queue: identical queue limit and loss (about 3.8 million
  points), but on recovery the RSS peaked at 3,891 MiB and the memory_limiter refused points for
  about one minute (up to 1,500 points/s), no restart. The persisted queue did not lower the memory
  peak at this size, unlike on the 6 node cluster of 2026-10-19; its value is that the queue survives
  a collector restart and can be far larger on disk than the 200,000 items in memory.
- 150 minute window at 1,461 pods (full catalog, 30 s interval, 60 s step): no refused point, no memory_limiter
  refusal, no restart; the cluster collector working set stayed between 2.2 and 2.8 GiB (garbage collection sawtooth
  around a flat level, with one step of about 150 MiB after the first hour: 2.42 GiB on average in the first 30
  minutes, 2.57 GiB in the last 30), RSS between 2.1 and 2.6 GiB, CPU between 0.17 and 0.28 cores; the node collectors stayed at 76 MiB working set and 153 MiB RSS on
  the busiest node. No growth beyond the sawtooth over 2.5 hours.
- Documented shape at 0 idle pods (271 pods): 0.05 cores, 570 MiB working set, 673 MiB RSS, 2,050 points/s,
  against 629 MiB at 1,461 pods: about 50 MiB per 1,000 pods, so the documented shape is flat in the pod count
  and the 4Gi limit is far from its ceiling there; the 570 MiB base is the kube-apiserver target (about 230,000
  series after the drop list of the monitoring stack) plus the 44 operator endpoints.

## What changes in the recommendation

The 2 CPU / 4Gi limits of the cluster collector hold up to about 1,000 pods with the full PoC catalog
(kubelet proxy jobs included) and leave room for an outage drain; at 1,500 pods the drain reaches the
soft limit and with `file_storage` the memory limiter refuses scrapes, so beyond about 1,000 pods either
leave the kubelet proxy jobs out (the documented shape: 0.05 cores and 630 MiB at 1,461 pods, the
`kubelet_stats` receiver covers the pods), or raise the limit to 6Gi (about 1.4 GiB per further 1,000
pods), or use the scale-out variant. The node collector and the documented shape need no change. CPU is
not a constraint anywhere: 0.24 cores for the cluster collector and 5 millicores per node at 1,471 pods.
