# k8s_cluster receiver against kube-state-metrics (2026-10-20)

Question from the review of the findings document: kube-state-metrics is tuned for clusters with many objects; does the
`k8s_cluster` receiver keep up? Both ran on the same OpenShift 5.0 cluster (7 nodes, 573 pods) against the same object
inventory, generated by `load/gen-objects.py` in the namespace `otel-load-objects`: 2,000 deployments (300 with a running
pod), 2,000 config maps, 500 services, 200 jobs, 200 suspended cron jobs, 300 horizontal pod autoscalers, 100 resource
quotas and 20 cluster resource quotas. The collector under test is `08-k8scluster-collector.yaml` (the `k8s_cluster`
receiver alone, 30 s interval, product collector 0.158.0, exported to the vendor Prometheus); kube-state-metrics is the
one of the monitoring stack, read through the platform Prometheus. `scripts/run-ksm-compare.sh` drives the phases and
`scripts/audit-requests.py` counts the API server audit events per service account.

Phases: baseline (10 min, empty inventory), create (the apply took 1,248 s), steady (20 min), restart (collector pod
deleted), churn (the 2,000 deployments deleted and recreated three times, 7 min apart), steady2 (10 min), timeline.
The collector was deleted by mistake between 12:24 and 12:37 UTC, between the create and the steady window; the
timeline chart shows the gap, no per-phase window includes it.

Result (`summary.md`, charts in `charts/`): both are small and alike at this inventory. The collector used 0.004 cores
and 136 MiB working set (212 MiB RSS) in steady state against 0.003 cores and 166 MiB (170 MiB RSS) for
kube-state-metrics; during the churn 0.006 against 0.006 cores with peaks of 0.012 and 0.013. Both saw the full
inventory while it was being applied (kube-state-metrics 3 s after the apply ended); after a pod restart the collector
reported the full inventory again after 35 s. Neither client lists objects after start-up: the audit logs show only
watch re-establishments (16 for the collector and 38 for kube-state-metrics in 20 minutes; 113 and 292 during the
churn). The 20 LIST/s on the API server while the inventory exists come from the horizontal pod autoscaler controller
(300 autoscalers polled every 15 s), not from the collectors, and vanish each time the deployments are deleted. The
kube-apiserver CPU rose from 0.72 to 0.85 cores (three instances) with the inventory and to 1.0 during the churn, the
same for both clients since they share the watch cache. What the collector does not have at this inventory is not a
performance gap but a coverage gap: no custom resource metrics (opentelemetry-collector-contrib#50196) and a fixed set
of kinds.
